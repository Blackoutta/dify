# Phoenix Workflow Tracing Backport for Dify 1.6

Date: 2026-05-12
Base branch: `1.6.0`
Upgrade target: `1.14.1` or newer, assuming the target contains upstream PR `langgenius/dify#35605`
Upstream reference commit: `7fc40e6c9ef7ec1caf03cd21aa40f52596b3954e`

## Purpose

Backport the Phoenix workflow tracing improvements from upstream PR
[`#35605`](https://github.com/langgenius/dify/pull/35605) to an older Dify `1.6.0` codebase without cherry-picking the upstream commit.

The backport must be a temporary, isolated patch. Before upgrading this branch from `1.6.0` to `1.14.1` or newer, the temporary patch should be reverted so the upgrade can use the upstream implementation instead of merging two different implementations of the same tracing behavior.

## Upstream Behavior To Preserve

The upstream PR fixes Phoenix workflow trace display for regular workflows, chatflows, nested workflows, and workflow-as-tool execution.

The behavior to preserve in the 1.6 backport is:

- top-level workflow and chatflow traces create stable Phoenix root/session semantics
- Phoenix workflow spans use a deterministic `session.id`
- nested workflows inherit the outer workflow or chatflow session when appropriate
- workflow node spans are reconstructed into a useful hierarchy instead of appearing flat or orphaned
- workflow-as-tool child workflow traces can attach back to the outer tool node span
- child traces that arrive before the parent tool span is published retry for a bounded period
- retrying provider dispatch does not duplicate enterprise or external trace dispatch if that concern exists in the target branch

## Key Difference From Upstream

The upstream commit was written against a much newer backend architecture:

- Phoenix provider code lives under `api/providers/trace/trace-arize-phoenix/`
- workflow tool execution flows through `api/core/workflow/node_runtime.py`
- workflow persistence flows through `api/core/app/workflow/layers/persistence.py`
- trace ID and parent-context helpers live in `api/core/helper/trace_id_helper.py`
- Graphon runtime protocol passes the current tool node execution id into runtime adapters

Dify `1.6.0` does not have those same entry points. Its Phoenix provider still lives under `api/core/ops/arize_phoenix_trace/`, and tool node execution is still wired through the older workflow graph engine. Because of that, a cherry-pick is the wrong tool. The 1.6 implementation should recreate the behavior in the 1.6 architecture.

## Approaches Considered

### Recommended: 1.6-native temporary backport

Implement the behavior directly in the 1.6 tracing and workflow execution paths. Keep the change in one isolated temp patch commit and revert it before upgrading to `1.14.1` or newer.

This is the best fit because it minimizes architectural drift in 1.6 and keeps the future upgrade clean.

### Not Recommended: cherry-pick upstream commit

Cherry-picking `7fc40e6c9e` onto `1.6.0` produces broad conflicts across provider packaging, workflow runtime, persistence, task dispatch, tests, and docker env files. Many of those conflicts reflect missing architecture rather than line-level edits.

### Not Recommended: forward-port new Graphon/provider structure into 1.6

Introducing newer Graphon/provider structure into 1.6 would create a large compatibility layer only to delete it during the `1.14.1` upgrade. That increases regression risk and makes the upgrade harder.

## Proposed 1.6 Design

### Phoenix provider

Modify the existing 1.6 provider at `api/core/ops/arize_phoenix_trace/arize_phoenix_trace.py`.

Responsibilities:

- create canonical workflow root spans for top-level workflow and chatflow traces
- set Phoenix `session.id` from `conversation_id`, outer workflow run id, or current workflow run id according to trace context
- reconstruct workflow node parentage using available 1.6 execution metadata and graph data
- publish outer workflow tool node span context to Redis when tracing a workflow tool node
- resolve child workflow parent span context from Redis when metadata includes a parent node execution id
- raise a core retryable exception when the child trace arrives before the parent span context is available

The Redis key should be short-lived and provider-local, for example:

```text
trace:phoenix:parent_span:<parent_node_execution_id>
```

The key should be safe to leave behind because it expires quickly and has no schema impact.

### Parent trace context propagation

Add a small typed or clearly validated parent context payload in the 1.6 trace path:

```json
{
  "parent_workflow_run_id": "<outer workflow run id>",
  "parent_node_execution_id": "<outer tool node execution id>"
}
```

In 1.6 this should be carried as internal metadata, not public workflow input. The design must avoid overwriting user-provided workflow inputs with the same key.

Likely 1.6 touch points:

- `api/core/workflow/nodes/tool/tool_node.py`
- `api/core/tools/workflow_as_tool/tool.py`
- `api/core/app/apps/workflow/app_generator.py`
- `api/core/ops/ops_trace_manager.py`
- `api/core/ops/entities/trace_entity.py`

### Trace task retry

Add a provider-neutral retry exception under `api/core/ops/`, then update `api/tasks/ops_trace_task.py` to:

- bind the Celery task so it can call `self.retry`
- retry only exceptions that opt into retry behavior
- keep the trace payload file only after Celery accepts the retry
- delete payload files after success, terminal failure, or exhausted retries
- increment the existing ops trace failure counter on terminal failure

The retry defaults should be configurable through the 1.6 config system and docker env examples. The upstream defaults are:

```text
OPS_TRACE_RETRYABLE_DISPATCH_MAX_RETRIES=60
OPS_TRACE_RETRYABLE_DISPATCH_DELAY_SECONDS=5
```

### Upgrade and revert strategy

The 1.6 backport must be committed as a standalone temporary commit, for example:

```text
temp: backport phoenix workflow tracing for dify 1.6
```

Before upgrading to `1.14.1` or newer:

```bash
git revert <temp_patch_commit_sha>
```

Then merge or rebase onto the target version. This avoids forcing Git to reconcile the 1.6-native backport with the upstream implementation that already exists in `1.14.1` or newer.

## Test Strategy

Focused tests should be added in the 1.6 test layout rather than copied from upstream test files directly.

Minimum coverage:

- Phoenix top-level workflow root span and `session.id`
- chatflow session behavior
- nested workflow session inheritance
- workflow node parent selection and fallback to workflow root
- workflow-as-tool parent context propagation without user input overwrite
- Redis parent span bridge success path
- missing parent carrier raises the retryable trace exception
- trace task retry keeps payload only when retry is scheduled
- retry exhaustion deletes payload and increments failure count

Manual verification should include a local Phoenix run through the branch-local docker middleware changes and a nested workflow-as-tool scenario.

## Risks

- The highest-risk area is recovering the outer tool node execution id in the older 1.6 workflow engine.
- Node hierarchy reconstruction may be less precise than upstream if 1.6 lacks newer Graphon metadata.
- Retry behavior must not create infinite retry loops or leave payload files behind after terminal failures.
- The temp patch must remain isolated. Business changes should not depend on it unless they are also reverted or adjusted before the `1.14.1` upgrade.

## Acceptance Criteria

- The backport is implemented in 1.6-native files, not by cherry-picking upstream.
- The backport is a standalone temporary commit.
- No database migration is introduced.
- Phoenix shows a stable workflow root/session for top-level workflows.
- Nested workflow-as-tool traces attach to the outer tool span when the parent span carrier is available.
- If the parent carrier is not yet available, trace dispatch retries within a bounded budget.
- The temporary backport can be reverted before upgrading to `1.14.1` or newer.
