# Phoenix Tracing 1.6 Backport Dev Diary

## Feature 目的

这个 feature 最初是把 Dify `1.14.1` 中 upstream commit `7fc40e6c9ef7ec1caf03cd21aa40f52596b3954e` 的 Phoenix workflow tracing 行为 backport 到 Dify `1.6.0`。目标是让普通 workflow、chatflow、workflow-as-tool 和嵌套 workflow 在 Phoenix 中拥有稳定的 root/session 语义、可读的节点层级，以及子 workflow 能挂回外层 tool node span。

后续又补充了一个 backend-only 的 Phoenix trace session override：调用 workflow/chatflow API 时可以传 `trace_session_id`，让 Phoenix/OpenInference `session.id` 使用外部业务 session，而不改变 Dify `conversation_id`、`workflow_run_id`、OpenTelemetry trace id、span id 或 Redis parent carrier 语义。

这个 backport 是 1.6-native 的临时补丁。`1.14.1` 的 upstream 实现依赖较新的 provider package、Graphon/runtime、workflow persistence 和 trace helper 结构，不能直接 cherry-pick 到 `1.6.0`。升级到 `1.14.1` 或更高版本前，应先移除这个临时 backport，再使用 upstream 实现，避免同时维护两套 Phoenix workflow tracing 行为。

## 实现与迭代过程

### 1. 放弃 cherry-pick，选择 1.6-native backport

前期设计确认 upstream 的目标行为包括：workflow/chatflow 的稳定 Phoenix root/session、nested workflow 继承外层 session、workflow node span 从扁平列表恢复成层级、workflow-as-tool child trace 能挂回外层 tool node span、child trace 早于 parent carrier 发布时可有界 retry。

对比后确认 `1.6.0` 没有 upstream 使用的新入口：provider 不在 `api/providers/trace/trace-arize-phoenix/`，workflow tool 不走新的 `node_runtime.py`，workflow persistence 也不是新版 layer 结构。因此实现选择在 1.6 现有路径内落地，不引入后续版本架构。

主 backport 汇总实现了：

- 增加 `ParentTraceContext`，用 Pydantic 强类型表示内部 parent workflow run id 和 parent node execution id。
- 从 `ToolNode` 到 `WorkflowTool` 再到 `WorkflowAppGenerator` 传递私有 parent context，避免覆盖用户输入中同名 `parent_trace_context`。
- 在 workflow/chatflow completion 路径和 `WorkflowCycleManager` 中把 parent context 带进 `TraceTask`。
- 在 `OpsTraceManager` 的 workflow trace metadata 中持久化 parent context，并补充 app/workspace name，便于 Phoenix span 命名和查询。
- 在 Phoenix provider 中创建 workflow root span、workflow span 和 node span，设置 `session.id`，并根据 1.6 的 graph/predecessor/loop metadata 重建 node parent hierarchy。
- 对 workflow tool node span 发布 Redis parent span carrier，child workflow trace 通过 `parent_node_execution_id` 读取 carrier 并 attach 到真实 parent tool span。
- 当 child trace 先于 parent tool span carrier 到达时，抛出 `PendingTraceParentContextError`，由 Celery trace task 进行有界 retry，并在 retry 被 Celery 接受时保留 payload。
- 增加本地 Phoenix middleware 支持，包括 docker compose service、middleware env 示例、`dev-down` 和 ssrf proxy loopback 访问。

本阶段保持了 upstream 的关键语义：child workflow 使用真实 parent carrier attach，而不是只靠逻辑 id 推断。

### 2. deterministic span id 方案被验证为错误并还原

review 中提出 Redis bridge 有时序依赖：child workflow trace 可能比 parent workflow trace 更早被 Celery dispatch。为降低等待 Redis carrier 的风险，曾尝试用 deterministic trace/span id 替代 Redis bridge：child workflow 根据 `parent_workflow_run_id` 和 `parent_node_execution_id` 本地构造 parent context。

手动 Phoenix 验证显示这个方向会破坏多层嵌套 trace：一次调用被拆成多条 trace，nested workflow root 出现在独立 root span 下。根因是多层嵌套时 `parent_workflow_run_id` 不是整条调用链的 trace root；真实 trace id 只能从已在 parent workflow trace 中传播的 carrier 获得。该尝试被完整 revert，最终方案继续保留 Redis carrier bridge。

### 3. 保守修复：保留 Redis bridge，修正 retry 窗口和 span 稳定性

还原 deterministic 方案后，只做不改变 parent attach 模型的保守修复：

- root span 使用 workflow `start_time` / `end_time`，避免 Phoenix 中出现 zero-duration root 或 child span 落在 parent duration 外。
- LLM node token attribute 的第二段解析也改用 `_extract_json_mapping()`，避免 malformed outputs 让单个节点中断整条 workflow trace dispatch。
- 增加测试覆盖 root span 时间边界、malformed LLM outputs，以及 retry budget 覆盖 workflow 执行窗口的目标。

retry budget 也从固定次数改为动态 effective retry limit：配置默认仍是 upstream 风格的 `OPS_TRACE_RETRYABLE_DISPATCH_MAX_RETRIES=60` 和 `OPS_TRACE_RETRYABLE_DISPATCH_DELAY_SECONDS=5`，但 Celery task 内部会用 `ceil(WORKFLOW_MAX_EXECUTION_TIME / delay)` 兜底，确保默认窗口不会短于 1.6 workflow 最大执行时间。

### 4. 收窄 retry 面：只对 pending parent carrier 做 Celery retry

进一步讨论嵌套很深时 retry 对 Celery worker 和 broker 的影响。结论是 `self.retry(countdown=...)` 不会占住 worker，但会增加队列中的 future retry task 和重复 payload/provider/Redis 操作。为降低 retry churn，保留动态窗口，但收窄 retry 适用范围：

- `process_trace_tasks` 只 catch `PendingTraceParentContextError` 并 schedule Celery retry。
- 普通 `RetryableTraceDispatchError` 不再触发 Celery retry，会按普通 trace dispatch failure 处理、计数并删除 payload。
- pending parent context 的正常重试日志降为 `info`；只有 retry budget exhausted 或 retry schedule 失败才记录 exception/failure。

这让 retry 只服务于本 feature 真正需要处理的异步竞态：child trace dispatch 早于 parent tool span carrier 发布。

### 5. Phoenix trace session id override：只改 `session.id`，不改 trace identity

新的需求是让 API caller 在触发 workflow/chatflow 时自定义 Phoenix/OpenInference `session.id`。设计阶段明确了边界：

- 字段名为 `trace_session_id`，是 observability hint，不进入 workflow inputs、node inputs 或 Dify conversation state。
- 当前阶段只做 backend 支持，不改 Web/Console 前端 UI 或 request builder。
- 只对 Phoenix provider 生效；其他 tracing provider 保持现状。
- 只影响 `SpanAttributes.SESSION_ID`，不改变 OTel `trace_id`、`span_id`、Dify `conversation_id`、`workflow_run_id` 或 Redis parent carrier bridge。

实现上新增集中 helper：`normalize_trace_session_id()` 和 `extract_trace_session_id_from_args()`，负责 trim、空值忽略、类型和长度校验。controller 只把可选 JSON 字段解析进 args；generator 通过 helper 放进 `AppGenerateEntity.extras`，避免把 trace 字段混入业务输入。

### 6. session id 在 workflow/chatflow/nested workflow 中透传

为了让 nested workflow 继承外层自定义 session，`trace_session_id` 从 app generator 继续传入 workflow runtime：

- `WorkflowEntry` / `GraphEngine` / `GraphInitParams` 增加可选字段，`BaseNode` 读取后供工具节点使用。
- `ToolNode` 如果拿到 workflow-as-tool runtime，会调用 `set_trace_session_id()`。
- `WorkflowTool` 在调用 child workflow generator 时把 `trace_session_id` 放回私有 generator args。
- loop/iteration 内部会新建 subgraph `GraphEngine`，review 时发现这里会丢失 session，因此补充 `trace_session_id=self.trace_session_id`，确保循环体里的 workflow tool 也继承外层 session。
- workflow completion、advanced-chat completion、message trace 都把 `trace_session_id` 传进 `TraceTask`，`OpsTraceManager` 再把非空字符串写入 trace metadata。

这个阶段重点保持 additive：所有新增构造参数都有默认 `None`，无字段时完全回退原行为。

### 7. Phoenix provider 消费 session override 并补 API 文档

Phoenix provider 的 workflow session resolution 从：

```python
conversation_id or parent_workflow_run_id or workflow_run_id or ""
```

变为：

```python
trace_session_id or conversation_id or parent_workflow_run_id or workflow_run_id or ""
```

message span、LLM child span、generate-name span 使用 `trace_session_id or conversation_id`。nested workflow 仍然通过 `parent_trace_context.parent_node_execution_id` 读取 Redis carrier；测试明确覆盖了 carrier lookup 仍发生，同时 `session.id` 使用自定义值。

最后补了英文 API 文档：`/workflows/run` 和 `/chat-messages` 的请求字段说明和 curl 示例都加入 `trace_session_id`，并说明它只设置导出到 Phoenix 的 OpenInference `session.id`，不会创建或恢复 Dify conversation。

## 当前实现模型

最终模型保留 Redis bridge：

1. workflow-as-tool 调用 child workflow 时，把私有 `ParentTraceContext` 放入 child workflow generation extras。
2. 如果 top-level request 提供 `trace_session_id`，该值通过 workflow runtime、tool node、workflow tool、loop/iteration subgraph 一路继承到 child workflow。
3. child workflow 完成后，trace metadata 中包含 parent context；如果有 custom session，也包含 `trace_session_id`。
4. parent workflow trace task 在处理外层 tool node span 时，把真实 OpenTelemetry carrier 发布到 Redis。
5. child workflow trace task 如果先到达，会因为 carrier missing 抛出 `PendingTraceParentContextError` 并 retry。
6. child retry 取到 Redis carrier 后，以真实 parent tool span 作为 parent context 导出 Phoenix span。
7. Phoenix `session.id` 优先使用 `trace_session_id`；没有该值时回退到 `conversation_id -> parent_workflow_run_id -> workflow_run_id`。

这个模型的关键点是：custom session 只是 Phoenix/OpenInference attribute，不参与 trace id 生成或 parent attach。手动验证已经证明 deterministic id 会导致同一次调用被拆成多条 Phoenix trace，因此不能用 custom session 替代 carrier bridge。

## 本地 Feature 测试覆盖点

- `ParentTraceContext` 强类型校验、metadata 解析、非法/不完整 payload 忽略。
- `trace_session_id` helper 覆盖 trim、空值忽略、非 string 拒绝、512 字符长度限制和 args extraction。
- workflow-as-tool 的私有 parent context 传递，不覆盖用户输入里的同名 `parent_trace_context`。
- tool node 能把外层 workflow run id、node id 和 trace session id 写入 workflow tool runtime。
- workflow、advanced-chat、loop/iteration subgraph 中的 trace session id 透传。
- workflow/message `TraceTask.execute()` metadata 中包含非空 `trace_session_id`。
- Phoenix provider 的 root/session 语义、workflow/node span 命名、node metadata attribute、loop/iteration 层级、repeated loop body 层级。
- Phoenix workflow root、workflow span、node span、message span、LLM child span 和 generate-name span 使用 custom `session.id`，并覆盖无 custom session 时回退原 conversation/workflow 语义。
- nested workflow 在 custom session 下仍然读取 Redis parent carrier，不改变 parent attach。
- Redis parent span bridge：缺少 carrier 时抛出 `PendingTraceParentContextError`，非法 carrier 被拒绝，tool node span 会发布 alias key。
- root span 使用 workflow 时间边界。
- malformed LLM outputs 不会中断 workflow trace dispatch。
- Celery trace task 在 pending parent context retry 时保留 payload，在 retry exhausted 时删除 payload 并增加失败计数。
- effective retry budget 覆盖 `WORKFLOW_MAX_EXECUTION_TIME`。
- generic retryable trace error 不触发 Celery retry，避免扩大 retry 面。
