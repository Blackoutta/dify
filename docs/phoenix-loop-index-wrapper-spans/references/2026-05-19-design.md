# Phoenix Loop Index Wrapper Spans Design

## Goal

Improve Phoenix trace tree readability for Dify loop and iteration executions by adding exporter-local wrapper spans for each `loop_index` and `iteration_index`.

The wrappers are display-only grouping spans. They must not change Dify workflow runtime behavior, persisted workflow node execution records, nested workflow parent carrier publishing, or API responses.

## Context

The Phoenix exporter currently maps workflow node executions to OpenTelemetry spans in `api/core/ops/arize_phoenix_trace/arize_phoenix_trace.py`.

Loop and iteration child nodes already carry metadata produced by the workflow runtime:

- `loop_id` and `loop_index` are attached by `api/core/workflow/nodes/loop/loop_node.py`.
- `iteration_id` and `iteration_index` are attached by `api/core/workflow/nodes/iteration/iteration_node.py`.

Today the exporter uses `loop_id` and `iteration_id` to parent all body nodes directly under the loop or iteration container span. This makes repeated body executions appear as a flat list. The desired trace tree should group body nodes by index so each run is easier to inspect.

## Recommended Approach

Add synthetic wrapper spans inside `ArizePhoenixDataTrace.workflow_trace()` only.

The exporter should use a precomputed grouping phase before node span emission:

1. Parse each workflow node execution's metadata.
2. Identify eligible wrapper groups.
3. Resolve each wrapper's real container execution id.
4. Compute each wrapper's start time, end time, and aggregate status from its grouped child nodes.
5. Create wrapper spans before emitting grouped child node spans.
6. End wrapper spans after all grouped child node spans have been emitted.

This keeps wrapper time bounds and parent relationships deterministic even though normal node spans are created and ended inside `emit_node_span()`.

For a node with:

```json
{
  "loop_id": "loop-node",
  "loop_index": 2
}
```

the exported tree should be:

```text
loop_main_loop
  loop[2]
    template-transform_Template
    tool_embedded_workflow_2_tool
```

For iteration nodes:

```text
iteration
  iteration[0]
    if-else_IF/ELSE_condition
    template-transform_Template
```

## Wrapper Semantics

Wrapper spans are synthetic and only represent UI grouping in Phoenix.

Each wrapper span should:

- Have name `loop[<index>]` or `iteration[<index>]`.
- Use OpenInference span kind `chain`.
- Use the same `session.id` as the workflow and node spans.
- Parent to the real loop or iteration container span.
- Become the parent of body node spans with the same container id and index.
- Carry metadata identifying it as synthetic:
  - `synthetic: true`
  - `wrapper_type: "loop"` or `"iteration"`
  - `wrapper_index: <index>`
  - `container_execution_id: <execution id of loop/iteration container>`
- Expose queryable attributes:
  - `dify.wrapper.synthetic`
  - `dify.wrapper.type`
  - `dify.wrapper.index`
  - `dify.wrapper.container_execution_id`

The wrapper start time should be the earliest child start time in that group. The wrapper end time should be the latest child end time in that group. The wrapper status should be `ERROR` if any child in the group failed, otherwise `OK`.

## Parent Resolution Rules

The exporter should keep the existing workflow/container parent behavior for nodes without index metadata.

When a node has index metadata:

1. If it has a valid `iteration_id` and `iteration_index`, use the matching `iteration[<index>]` wrapper as the parent.
2. Otherwise, if it has a valid `loop_id` and `loop_index`, use the matching `loop[<index>]` wrapper as the parent.
3. Otherwise, fall back to the current structured parent span resolution.

Iteration wins over loop when both are present because it is the more specific grouping.

Wrappers should only be created when the container graph id resolves to one unambiguous execution id through `_build_execution_id_by_node_id()`. If the container graph id is missing, duplicated, or otherwise cannot be resolved to a single execution id, no wrapper should be created for that group and affected nodes should use the current structured parent span resolution.

Valid index values are:

- Integers, excluding booleans.
- Non-empty strings matching `^[A-Za-z0-9_.:-]+$`.

String indexes should be preserved exactly in wrapper names and attributes. Floats, booleans, empty strings, whitespace-padded strings, negative integers, and strings containing characters outside the allowed pattern should be treated as malformed and should fall back to current behavior.

## Nested Workflow Carrier Behavior

Tool node spans must continue to publish parent carriers from the tool node span itself.

Wrapper spans must not publish parent carriers. A nested child workflow should still attach below the tool node span, not below the synthetic wrapper. The wrapper only changes the tool node's immediate parent in the visible trace tree.

Tests should observe this by asserting that carrier publication is triggered only for tool spans, and that injected carrier context corresponds to the tool span rather than the wrapper span. No publish call should occur for wrapper spans.

## Child Node Attributes

Child node spans must keep their existing metadata and queryable attributes.

When present, the exporter should also expose index metadata as queryable child node attributes:

- `dify.node.loop_index`
- `dify.node.iteration_index`

## Error Handling

If a wrapper's container span cannot be found, the exporter should fall back to the current parent resolution rather than failing the whole trace export.

If index metadata is present but malformed, the exporter should ignore the wrapper path and keep current behavior. Valid index values are integers or strings that can be represented clearly in the wrapper name and attributes.

## Testing

Tests should be added to `api/tests/unit_tests/core/ops/test_arize_phoenix_trace.py`.

Required coverage:

- Loop body nodes with the same `loop_id` and different `loop_index` values are grouped under distinct `loop[0]`, `loop[1]` wrapper spans.
- Iteration body nodes with the same `iteration_id` and different `iteration_index` values are grouped under distinct `iteration[0]`, `iteration[1]` wrapper spans.
- Nodes without index metadata keep the current parent behavior.
- The existing `test_workflow_trace_keeps_repeated_loop_body_nodes_under_loop` should be updated or split so index-bearing loop body nodes test grouped behavior, while a separate no-index regression test preserves flat parent behavior.
- Ambiguous duplicate container graph ids do not create wrappers and fall back to current parent behavior.
- Tool nodes inside a wrapper still publish parent carriers and nested workflow attachment remains based on the tool span.
- Wrapper spans use the expected time bounds and status aggregation.
- Child node spans expose `dify.node.loop_index` and `dify.node.iteration_index` when those metadata values are present.

## Scope

In scope:

- Phoenix/Arize exporter span tree shape.
- Unit tests for wrapper grouping and carrier preservation.

Out of scope:

- Runtime event changes.
- Database schema changes.
- Dify workflow run API changes.
- Phoenix UI changes.
- Persisting wrappers as real workflow node executions.
